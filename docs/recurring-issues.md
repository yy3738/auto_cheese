# 反复出现的问题登记册

> 创建 2026-10-22。这里只收**同一种病复发过两次以上、或同一轮返工三次以上**
> 的问题类型:每次复发都要先对照本表,而不是从零重新排查。
> 单次故障的排查史见 [overlay-auto-recognize-status.md](overlay-auto-recognize-status.md),
> 通用工程经验见 [development-lessons.md](development-lessons.md)。

## 〇、复发类型速查

| # | 复发类型 | 典型症状 | 第一步动作 |
|---|---|---|---|
| 1 | 同一症状多病因 | 「识别不出来」 | 先分层定界,再谈修复 |
| 2 | PC 与 App 口径不一致 | PC 全对、App 全错 | 用 App 自己落盘的同一帧对拍 |
| 3 | 识别层追动画 | 阈值越调越糟 | 改到循环层/仲裁层容忍 |

## 1. 同一症状多病因：「识别不出来」

复发 5 次以上,已确认的独立病因:

| 病因 | 数据特征 | 修复 |
|---|---|---|
| 白光圈罩空位/罩棋子 | 空位 std 抬高;被罩棋子周期性翻版 | 像素预剔除 + 循环层双向遮蔽容忍 |
| 悬浮窗压进识别区 | row0 持续 unknown,d=1.0 | 默认位置移到棋盘下缘之外 |
| 引擎无 bestmove | 有候选、深度在涨,面板不更新 | stop 后补等 2s,go 前清残留队列 |
| 循环不挑前台 App | 对着自家主界面/实况页识别,全帧低置信 | 前台判定(UsageStats 主轨 + 边条指纹兜底) |
| 授权/服务状态错位 | 「授权后请再点一次」反复出现 | 双重启门禁 + 授权成功即自动启动 |
| 校准文件倾斜 | 单格持续误读,其余全对 | 删校准重做 / PC 对比两套四角 |

**纪律**:报「识别不出来」先问三件事——报错在识别层、仲裁层还是引擎层?
当前前台是不是 JJ?设备上跑的是不是刚编出来的 APK?三者先定界,再动手。

## 2. PC 与 App 口径不一致(复发 2 次,每次浪费半天)

- **2026-09**:PC 原型用 `refine_grid` 吸附网格,App 用 raw 双线性网格,
  PC 全对、App 复现失败。
- **2026-10-21**:PC 训练用 PIL `BILINEAR`,App 的 `FrameSampling` 用面积均值。
  NN 输入 104→128 上采样时面积均值退化成块复制马赛克,模型在 App 内置信
  整体塌到 0.6-0.9 全体拒判;PC 对同一张帧 81/86 正确。改为 4 邻点双线性后
  恢复。
- **2026-10-21(同一轮)**:App 落盘帧在 PC 端 86/90 正确且无幻影,App 内
  每帧多一个红车。唯一差异是 Kotlin 端自己加的翻转 TTA → 撤 TTA。

**纪律**:
1. 复现识别问题,必须拿 **App 自己落盘的帧**(`files/dump/`、`_appframe.png`),
   不要用 adb screencap 代替——两者可能来自不同管线。
2. 任何缩放/裁剪/归一化改动,PC 端评估脚本与 Kotlin 实现必须逐参数对齐
   (插值方式、crop 边界、通道顺序、mean/std、是否 TTA)。
3. 对拍顺序固定:**同帧 → 同模型 → 先排除模型,再怀疑采样**,最后才怀疑
   模型本身。

## 3. 识别层追动画(复发 3 次)

光圈脉动、落子标记、入场飞子都属于**动画类污染**,任何逐格阈值(NCC 距离、
std、CNN margin)都会被它推着走:

- 白光圈把空位 std 抬过判空阈值 → 误判有子;
- 光圈呼吸使被罩棋子每分钟翻版上百次 → 循环无限重算 + 候选跳变;
- 入场动画的飞子被高置信读成真实棋子 → 假局面。

**正确层次**:识别层只负责"读出它看到的",**动画容忍放在仲裁/循环层**——
仅消失=忽略、仅出现=修正锚点、连续两帧一致才落定、变化格必须能解释成
合法单步。不要靠调识别阈值去追动画。

## 4. 状态与缓存不同步(复发 2 次)

- **懒推理指纹不同步**:`CnnEngine` 只重推理 dirty 格,却把 `cachedFp`
  整体覆盖 → 冻结期分类与指纹错配被永久固化。修复:指纹逐格随分类同步
  (`cachedFp[i] = fp[i]`,且只对实际推理成功的格)。
- **锚点回填吞变化**:拒判格一律回填锚点旧值 → 对方落点被回填回旧值,
  局面恒等于锚点、永不记账(实测 8 分钟零 step)。修复:锚点帧存每格
  4×4 灰度快照,拒判格用像素差分判真实变化,只有真静止才回填。

**纪律**:凡是"缓存/锚点/旧局面 + 每帧部分更新"的设计,先写出**所有副本
清单**,逐个确认更新条件;新增字段时问一句"冻结期它会不会过期"。

## 5. 方向与符号约定(复发 3 次)

| 约定 | 坑 | 结论 |
|---|---|---|
| 矩阵 row0 | 识别矩阵 row0=屏幕最上排;Position/FEN row0=黑方底线 | 必须经 `normalizeOrientation` |
| 行号基数 | 用户报"第 4 行"是 1 基,脚本/标注是 0 基 | 入库前用坐标回问确认 |
| 执黑局锚点域 | lastGood 存 normalize 后局面、raw 草稿比较 | 锚点统一 raw 域 |
| margin 符号 | `sigmoid(top1-top2)`;某脚本写成 `sigmoid(top2-top1)` | 漏负号导致 100% 拒判 |
| 记谱纵线 | 双方都从屏幕右侧数 1-9 | 与用户口径一致 |

**纪律**:跨语言/跨端传递的每个方向性量(row、col、diff、sign、翻转),
在两侧各写一条注释说明符号方向;改完至少用一帧已知局面双向验证。

## 6. 改动未生效(复发 4 次)

行为与修复前**完全一致**时,先怀疑改动没上设备,而不是修复无效:

1. `assembleAndroidTest` 不重编主包;后台 gradle 可能停在 install 前。
2. 多设备在线,`adb` 未带 `-s` 也可能装到了另一台。
3. 重装后 MediaProjection 授权必失效,服务没跑起来时一切"无反应"。
4. 判断办法:`dumpsys package com.cheese.assistant | grep lastUpdateTime`,
   以及比对设备端日志里的关键字符串是否含本轮新增内容。

## 7. 归因臆测(复发 2 次,代价最大)

- 把石纹空格的 CNN 拒判臆测成"JJ 换皮肤了",回查历史局影子日志发现同皮肤、
  同格子拒判早已占 91-98% 帧——实际是训练数据缺样本。
- 把识别不稳归因成"新域/新分辨率",无任何数据支撑。

**纪律**:任何归因先给出**可对照的数据**:同一格子历史帧表现、同帧 PC 端
推理、相邻帧 FEN diff。拿不出数据就写"未定位",不许猜。用户已有方案时
执行用户的方案,不自行发明改法;已定架构(CNN 主路)内不得擅自塞回退役
组件(NCC)。

## 8. 静默路径(复发 2 次)

- `pendingConfirm` 阶段条件不满足时,循环只做 `contentEquals` 判断,
  既不推新帧也不打日志 → 用户看到"十几秒不出推荐",日志里一片空白。
- 开局守门拦住 31 子残缺盘后,30s 超时强制接受,期间没有任何可见提示。

**纪律**:每个"本轮不做任何事"的分支至少要有一条**限频日志**(或面板状态),
说明在等什么、已等多久。排查时,"没有日志"本身必须能被区分成"没跑"
和"跑了但静默"。

## 9. 外部操作纪律(自动化测试)

- 远程 adb 驱动(force-stop / am start / monkey)会顶掉用户正在进行的
  对局、实况页与静音状态,多次制造"识别不出来"的假象。**用户明令:
  Claude 不主动操作设备界面,由用户测试。**
- 必须操作时:先截屏确认当前页面,单步执行,操作后立即截图留证,
  不连续点按。
- 所有 adb 命令固定 `-s 127.0.0.1:5555`(本机常有两台设备在线)。

## 10. 重装后的手工复位

每次 `install -r` 后用户都要点「结 & 下一局」清旧棋谱,否则新局会追加到
旧棋谱上。已修复为**安装事件自动清盘**:读 `PackageInfo.lastUpdateTime`
与 `versionCode`,与 prefs 里记录的 `cleared_last_update/cleared_version`
不一致即清 `files/state/`。

**纪律**:凡是"跨进程持久化 + 与安装版本强相关"的状态(FEN、棋谱、锚点),
都要绑定安装事件清理,不要指望用户记得手动复位。

## 11. 棋子无故消失（少子，2026-10-22 定位并根治）

**症状**：开局提醒「兵九进一」很久；对局几步后左上黑车/黑马从推荐与
棋谱里消失；实况页「棋谱与识别不一致」。

**实测链路**（`_today.log` / `_y.log`）：
1. JJ 红色落点/威胁标记套在黑子上 → CNN 把黑车读成红车（合成同帧复现：
   黑车+红圈 → `R_ROOK` 置信 0.94-0.99；重训加红圈增强后 → `B_ROOK` 1.0）。
2. `piece cap` 看到 3 个红车，按 margin 剔除“多的那个”——被剔的正是真黑车。
3. 残缺盘（31 子）命中「载入期残缺盘」，30 秒后**强制接受** → 首推兵九进一。
4. 中局 `vanish-only ×10` 自动重锚、`implausible ×3` 自动清谱采纳，把错盘永久固化。

**修复**（2026-10-22，用户确认）：
- 识别层颜色门：按格内最暗 18% 笔画 `R-G`（黑≈1-3 / 红≈76-113）纠正红黑；
  指纹扩到 5×5 并加颜色项；新增 `invalidate(cells)` 强制重推。
- 同型超限**绝不删子**：先按期望局面（棋谱回放/recorder 基准/START）逐格
  核对；仍超限整帧作废并强制重推。
- 三处自动逃生门改为「保留锚点/棋谱 + 强制重推 + 悬浮窗提示」，不自动
  采纳“棋子凭空消失/出现”的帧。
- 30 秒超时不再强制接受残缺盘；期望局面有、本帧空的棋子按子集规则补回
  （`BoardRepair.restoreMissing`，缺失 1-3 格）。
- 模型重训：类内近重复只留一张、空位硬负样本必进、红圈/绿圈同时套
  黑子/红子/空格。留出 109/110、硬错 0、空位硬负误报 0/67（旧 46/67）。

**纪律**：象棋里棋子只能被吃，不能凭空消失；任何“修复”如果减少棋子，
必须先证明是幻影，否则拒绝该帧。

**2026-10-22 补**：中局棋谱漏记吃子后，"期望有、本帧空"的回填会把已被吃
的子每帧补回来（实况页第三列多出两个车）。修复用**木色占比**裁决：棋子
`R-B>40` 占比 0.56-1.00，空位 0.00-0.02；冷格说明真被吃/走开，不补。
vanish-only ×10 也用同一证据：暖格=误读（保留锚点重推），冷格=真消失
（以当前帧重锚）。

## 12. 引擎"搜索太快"（2026-10-23 定位并根治）

**症状**：推荐/复盘出现 `fast search cost=29-90ms depth=3-7`；复盘标称
3000ms 实际 30-50ms；知识库全是浅结果。表面上"反应很快"，实为搜索被掐断。

**病因**：`pikafish_jni.cpp` 的 `nativeGo` 绕过 UCI 层直接
`g_engine->go(limits)`，只设了 `limits.movetime`，**没设 `limits.startTime`**
（UCI 入口 `uci.cpp:195` 才会设）。`TimeManagement` 用
`elapsed = now() - startTime`，startTime=0 时 elapsed 是天文数字，
第一次时间检查就 stop。

**修复**：JNI 里补 `limits.startTime = steady_clock now(ms)`。
验证：游戏搜索 `cost≈600ms depth≥10`、复盘 `cost≈3000ms`，不再出现
`fast search` 警告。

**纪律**：任何绕过 UCI 文本层直调 `Engine` 的接口，必须自己补齐
UCI 层做的初始化（startTime / 合法局面 / 选项），否则引擎行为会静默异常。

## 13. 同一棋子正反来回记步（幽灵步复发，2026-10-23）

**症状**：日志里同一个红马 0.7 秒内被记 `(9,7)→(7,6)` → 反向 → 再正向；
棋谱多出"走一步又退一步"，伴随 `turn desync`。

**病因**：S1b 帧环接上后，识别循环在没有落定窗口时仍回退
`captureFresh`/`lastBmp` 抓任意帧识别——动画中或落后的画面被当成新盘面。

**修复**：帧环开着时只认落定帧；动画中/落定未到直接返回上一次局面
（不抓帧不记谱）；只有首次启动（`lastObserved==null` 且未在动画）或
长时间无落定（静止 1.5s / 动画 3.5s 异常逃生）才允许兜底抓帧。

## 14. 边条指纹单帧误判丢步（2026-10-23）

**症状**：偶尔漏记一步（日志 `turn desync`），多发生在弹窗/切页/实况页
来回的瞬间。

**病因**（代码级，非猜测）：`waitForPosition` 先 `pollSettle` 取走落定窗口，
再做边条指纹校验；校验不符时**直接 `clearSettles()` 丢掉这个窗口**——
单帧误判（`识别暂停 ×1`）就把这一步棋永久丢了。附带缺陷：
`mismatchRun` 成功时从不复位，间歇性误判累积到 60 会假"重学"边条指纹，
之后非对局画面也可能被放行。

**最终修复（2026-10-23）**：边条指纹降级为**提示**——不符时容忍前 2 帧
（继续走识别，由双王/子数/期望门把关），连续 3 帧不符才暂停，60 帧才
重学指纹；识别成功即 `mismatchRun = 0`。中间加过的 `deferredSettle`
重试机制已删除（无上限会活锁；加上限后仍每手白烧 1.1s，因为判据本身
就是错的）。日志保留 `边条指纹不符 top=… bot=…` 比值，便于继续标定。

## 15. 帧环落定窗口被兜底抓帧顶掉（2026-10-23）

**症状**：同一棋子被记成正反两步、`turn desync`（棋谱多出"走一步退一步"）。

**病因**：帧环开着但没等到落定时，识别循环回退 `captureFresh`/`lastBmp`
抓任意帧识别——动画中或落后的画面被当成新盘面。

**修复**：帧环开着时只认落定帧；动画中/落定未到原样返回上次局面
（不抓帧、不记谱、不出提示）；仅首次启动或长时间无落定（静止 1.5s、
动画异常 3.5s）才兜底。

## 16. 红车被读成黑车 → 棋谱永久错乱（2026-10-23）

**症状**：用户吃掉对方一个车后，App 的盘面里对方仍有两个车；此后每帧
`implausible ×3`，十几秒不恢复（`永不恢复`）。

**实测链条**（`app-1023-172631.log`）：
1. 17:42:19 红车吃黑士走到 `(0,5)`，棋谱正确（`rn1akR3`）；
2. 17:42:30 `color gate: R_ROOK→B_ROOK at (0,5) R-G=31.5`——颜色门按
   "笔画最暗 18% 的 mean(R-G)" 判色，该格只有 31.5（红子正常 p5≈76，
   黑子 p95≈2.8），落在 35 的阈值内被改判成黑车；
3. 仲裁层 `retag confirmed` 两帧后**采纳**了改判 → 黑方凭空多一个车；
4. 之后每帧差异都是"红车→黑车"这种非法走子，`implausible` 无限空转。

**修复（两道防线 + 一个逃生门）**：
- `BoardRepair.fixColors`：同兵种异色的**静态格**按期望局面（棋谱当前
  局面）纠正。颜色在象棋里永不改变，静态格上的同形异色一定是误配。
- `MoveCheck.exceedsMaterialCount`：单格改判若让某一方凭空多子（棋子
  只减不增）直接拒绝，并强制重推该格。
- 逃生门：`implausible` 连续 4 轮（约 5s）解释不了，就以识别盘为当前
  局面继续并留缺口 + 悬浮窗提示纠错，不再无限空转。

**纪律**：任何"改判/纠错"都必须过**物料不变量**（每方每兵种数量只减不增）。

## 17. 纠色把用户刚走的子改回去（2026-10-26 回归）

**症状**：用户红车吃掉黑车后，盘面/推荐里那颗红车又变回黑车。

**实测链条**（`app-1026-102211.log`）：
1. 10:23:56 棋谱记录黑车吃红车，`(8,3)` 是黑车；
2. 用户走 **车九平六**（红车 a1→d1 吃这个黑车），画面 `(8,3)` 变红车、`(8,0)` 变空；
3. 10:24:01 `expected-color fix: (8,3)→车` 拿旧棋谱把红车改回黑车
   ——因为 `fixColors` 判"该格静态"用的是**灰度快照**，同格红车↔黑车灰度
   几乎一样，刚走完的子被当成"静态误配色"；
4. 下一帧变成"红车凭空消失"，仲裁层再拆出不可能的两步，整盘错乱。

**修复**：`fixColors` 只在"整帧与棋谱的差异**全部**是同兵种异色"时生效；
一旦出现某格变空/多子（真实走子/吃子的特征）立刻放弃纠色。灰度不辨颜色，
所以"静态"这一条必须配这条才安全。

**纪律**：任何"按旧状态修正新观测"的逻辑，先问"新观测里有没有走子差异"——
有走子就说明旧状态已过期，不能拿它改。
