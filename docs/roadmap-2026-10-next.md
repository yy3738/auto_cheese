## 一、S4：引擎体验（本轮实施）

### 已具备
- 首推库优先（S3 前）：KB 命中秒出，后台补两条
- JNI `limits.startTime` 修复：movetime 真生效（900ms 实战 / 3000ms 复盘）

### 实施结果（2026-10-26，全部完成）
1. **进程级 `EngineHolder`**：NNUE 加载 + warm-up 从 service 提前到进程
   （`CheeseApp.onCreate` 预热点火），Service 与主界面分析共用同一个
   `SearchController`（JNI 是进程级单引擎，绝不能两个 controller 抢）
2. **状态可见**：加载中显示「引擎预热中 Xs」；就绪后正常分析；
   失败显示原因（不再静默）
3. **渐进首搜**：`SearchController` 解析 `info` 行时，首个"完整 MultiPV
   候选集"到达即回调，先上屏一条/一组，`bestmove` 后最终结果覆盖
4. **自适应 movetime**：终局深度不足（<12）且耗时未超上限时，用
   1800ms 再搜一次（只对用户回合的非库局面），把"慢机浅搜索"补回来
5. 验收：预热在开局前完成；首条候选 ≤1.5s（引擎已就绪时）；复盘仍 3000ms
6. **实测**（Android 14 模拟器）：进程启动后 15.1s `Engine: ready`；
   主界面与悬浮窗共用同一 controller
7. **2026-10-26 当天回退渐进/补搜**（用户反馈"先出一批、过一会儿又换一批、
   顺序还变"）：深度 5 的临时候选没有参考价值，浅深度补搜又必然改结果。
   现在**一次搜索只出一次结果**，基础 movetime 900→1200ms 补深度。
   `SearchController` 的 onPartial 能力已移除，避免再次误用

### 生命周期
- `EngineHolder` 随进程存活（用户接受约 64MiB NNUE + Hash 内存）；
  进程死亡自动释放；主界面/服务停止不清引擎
- 复盘与实战分析共用引擎时用 `searchMutex` 串行（后续 B 项再细化优先级）

## 二、B：异步复盘（待细化）

现状：点「结」后复盘占用引擎、按钮锁在「复盘中」，用户要等几分钟才能开新局。

目标：复盘进独立 job，**立即回到局前态可开新局**；复盘完成用通知/悬浮窗
提示。开放问题：新局实战分析与后台复盘抢引擎时的优先级（建议：实战优先，
复盘在两次分析之间跑；或复盘期间把 movetime 降到 1500ms）。

## 三、C：复盘回放 + 棋理解释（待细化）

现状：复盘结果只有「失误/大漏着」计数与列表。
目标：复盘页点某一步 → 棋盘渲染该步局面 → 文本说明"为什么这步差/好"：
- 数据来源：`GameReviewer` 已有的逐局面评分差、`ThreatMarker`（吃/将/威胁）、
  `ReviewLogic` 的 blunderLevel
- 交互：复用 `BoardView`（只读模式）+ 上一步/下一步/自动播放
- 开放问题：解释文案的粒度（评分差 + 威胁类型 + 一句棋理），是否要引用
  最佳着法的 PV 前 2-3 步

## 五、E：暂停/继续/结束（待细化）

状态机建议：
```
局前(开局) → 运行中(暂停 | 结) → 已暂停(继续 | 结束) → 复盘(异步) → 局前
```
暂停语义（待确认）：
- 暂停期间停止采集与推荐，但保留锚点/棋谱；继续后从当前盘面重同步
- 「结束」= 封存 + 异步复盘（与 B 联动）
- 暂停时悬浮窗是否收起/变灰、是否仍显示上一手
