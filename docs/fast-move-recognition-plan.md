## 一、问题与数据（全部来自实机日志）

### 1.1 快速下子漏步（用户主诉）

当前识别循环是**串行**的：

```
抓帧 → captureStable(350ms×2) → CNN(0.1-0.6s) → 记账
     → 同步等引擎分析(movetime 600ms，模拟器实际 3.7s) → 下一帧
```

- 引擎分析期间**不抓帧**，这是最大盲区；
- 抓帧本身 1-2s；对手/用户在这段时间连走两步，回来只剩净变化 4+ 格；
- `tryTwoSteps` 只在“非法单步”分支跑，只做形状判断、不查棋规、不利用移动标记；
- 中间那一步的稳定画面没有被保留（`ImageReader` 只取 latest，旧帧丢弃）；
- 实测 16:52:08 第 12 手后，16:52:24 用户点重试；重试在“进黑车 + 平红车”两步已走完的盘面上重启，旧版静默跳过两步，回放从第 15 手断裂。
- 实测 17:51:25-33 红马 `(9,7)→(7,6)` 被 `origin static` 拒绝 10 帧（9s）才放行；17:51:24 `piece cap B_KNIGHT expected restore (7,6) → 空 [static]` 用过期期望删了真黑马。

### 1.2 开局慢

```
17:49:30  service 创建（开始预热）
17:49:40  点「开局」
17:49:49  SearchCtl: warm-up done 3033ms
17:49:57  用户点重试（restart reconcile 补记红炮）
17:50:01  首推荐（movetime 600 实际 3678ms）
```

- NNUE 64MiB 加载/校验 ~16s + warm-up 3s + 首搜 3.7s；
- 预热从 service onCreate 才开始，只和开局前 10 秒重叠；
- 用户在无反馈的等待中点重试，虽然现在能补记，但额外增加 16s。

### 1.3 复盘进度

- 已实现但只在正文：`SealReview: progress 0/1 → 1/1`，`Overlay setText len=14`；
- 短局只有 1 个用户局面，6 秒结束；按钮始终是「复盘中」，看起来像没动。

| 层 | 现状 | 瓶颈 |

## 四、详细设计

### 4.1 采集层：事件驱动的细胞状态流（动画感知）

**先结论**：异步只拿掉“引擎分析时的盲区”；快棋漏步的根在**采集与帧比对**。
现有 `captureStable` = 「每 350ms 取两帧 + 棋盘区 2304 点全局灰度差 ≤96」，
有两个硬伤：

- 看不到 <350ms 的中间平台（AI 落子后、我方落子前的短暂稳定）；
- 分不清“棋子在飞/光圈脉动”与“棋子真的变了”，要么误判动画帧，要么空等。

#### 4.1.1 逐帧细胞状态（60fps，不在帧上跑 CNN）

- `ImageReader` 改为 `OnImageAvailableListener` 驱动，`maxImages=6`；
- 直接在 `Image.plane` 上采样，**不把整帧转 Bitmap**；
- 每帧只算 90 格：
  - 木色占比 `warmth`：棋子存在性（实测棋子 0.56+ / 空位 0.02-）；
  - 5×5 指纹：棋子类型/颜色（复用 `cellFp`，含颜色项）；
  - 白圈/红圈标记位：最后一步起点/落点（辅助）；
  - 边条指纹：前台判定（限频）。
- 环形缓冲最近 **3 秒**（约 180 帧 × ~1KB，只存细胞状态；覆盖对方 AI 0.5-1s / 人类 1-3s 的短窗口）；
- 整帧 Bitmap 只在“平台/落定”帧保留（≤6 张），供 CNN 与落盘；
- 失败/异常窗口整段落盘，用于阈值标定。

#### 4.1.2 动画状态机（关键设计）

```
STABLE(board) --检测到非装饰格变化--> MOVING(startFrame)
MOVING:
  每帧记录：变化格集合、warmth、指纹、markers
  非标记格状态连续 >= PLATEAU_MS 不变 -> 平台（候选中间盘）
  非标记格状态连续 >= SETTLE_MS 不变且 markers/边条稳定 -> 落定（结束盘）
  落定后回到 STABLE(结束盘)
```

- **STABLE**：与最后稳定盘一致；无变化。
- **MOVING**：至少一格细胞状态变化（棋子存在性/类型变化，不含光圈脉动）；
- **平台 PLATEAU**：MOVING 中一段非标记格稳定 ≥80-120ms → 中间盘面
  （AI 落子后、你落子前的那段“想棋”时间就是天然平台）；
- **落定 SETTLE**：非标记格稳定 ≥120-200ms，且白圈/红圈/边条不再跳变 → 结束盘；
- **两连手**：一个 MOVING 窗口里出现两个平台/两个落定 → 直接得到中间盘和结束盘；
  中间平台 < 阈值没抓到 → 交给 4.3 的 1-4 步还原；
- **标记装饰**（白圈/红圈脉动）默认**不计入**“棋子变化”，单独存为消歧信号。

#### 4.1.3 动画期间如何分类

- **飞行帧不送 CNN**：棋子在空中/缩放时分类不可信（历史教训：入场动画飞子被
  高置信读成中间位假子）。
- CNN 只在 **平台帧 / 落定帧** 上跑，且只重推变化格（懒推理）；
- 落点格可能仍有红圈：颜色门按“最暗 18% 笔画”判色，不受圈影响；
  木色占比判存在；两者共同确认“这格是什么”。
- 落定帧上检测白圈/红圈，**只作低优先级佐证**，不作为落定的必要条件。

#### 4.1.3b 语义稳定 vs 像素稳定（用户实测补充）

- **稳定性用语义盘面判断**：CNN 的 棋子/空 + 类型/颜色 + 置信，而不是原始像素指纹。
  像素指纹变化只负责“触发该格重推”，不直接等于“棋子变了”。
- **点选抬起**：用户点击棋子时整体上移一点，单格像素会变，但语义通常不变
  → 不产生走子；若 CNN 把它读成 UNKNOWN/空，用锚点回填/等待，不落子。
  抬起的稳定帧也不能被当成“棋子消失”的落定盘。
- **白圈会停留到下一步**：它是装饰标记，不是主信号。`MoveMarkerDetector`
  只做歧义投票/日志佐证，不参与“是否落定”的必需条件（用户明确：不要过度依赖白圈）。
- **用户思考 2-3s**：AI 落子后的中间平台天然足够长，必被 PLATEAU 捕获；
  真正要处理的是“我方落子 + 对方秒回”这个短窗口（交给帧环 + 1-4 步还原）。
- 用户点击/抬起/拖动的帧：状态机进入 MOVING 但**不落定**；等释放后的稳定帧。

#### 4.1.4 阈值标定（必须用真实动画帧）

- 已验证的时序假设（用户 2026-10-23）：
  - 走子动画 = **滑行/飞行**；
  - 白圈会**停留到下一步**（不是瞬时）；
  - 我方思考 2-3s 后才点棋子；点选时棋子上移（单格像素变、语义不变）；
  - 对方 AI 落子 **0.5-1s**；对方人类 **1-3s**；
  - 因此 AI 落子后的中间平台足够长，PLATEAU 必能捕获；关键短窗口是
    “我方落子 + 对方 AI 0.5-1s 秒回”，3s 帧环覆盖；常见 N=2，N=3/4 兜底。
- `PLATEAU_MS` / `SETTLE_MS`、指纹/木色变化阈值**不能拍脑袋**：
  每次 MOVING 窗口落盘（时间戳、变化格、warmth、markers、缩略图），
  用 1-2 局真实对局回放标定；
- 目标：对方动画结束后 ≤200ms 判定落定；中间平台 ≥80ms 即可捕获；
- 如果 JJ 的动画是“棋子直接消失+目标处淡入”，则平台检测更稳定；
  如果是“飞行动画”，飞行帧只用于时间线，不分类。

### 4.2 识别层：按平台/落定帧懒推理

- 每个平台/落定帧只对**变化格**做 CNN 推理（现有懒推理）；
- 颜色门（R-G 笔画）继续纠红黑；
- 期望可信门继续生效；
- `MoveMarkerDetector`（**可选佐证，不是主信号**）：
  - 白圈（亮、低饱和）→ 最后一步**起点空格**；白圈会停留到下一步，不能当“正在走子”的判据；
  - 红圈（R>170、R-G>120）→ 落点/威胁（辅助）；
  - 输出 `lastMoveOrigin` / `lastMoveDestHint`，只在平台/DFS 出现多解时参与投票与日志；
  - 没有白圈/红圈也必须能正常工作；当前皮肤语义仅作标定参考。
- 平台/落定帧的**语义盘面**交给 4.3 的序列还原。

### 4.3 记账层：1-4 步合法序列还原

输入：`prev`（最后接受局面，含行棋方）、`cur`（当前盘面）、帧环平台、移动标记。

```
resolveSequence(prev, cur, plates, markers):
  1. 若 plates 有中间平台：
      把平台序列解释成逐步盘面，逐手用 legalStepPair 校验；唯一则记账。
  2. 否则 DFS（最多 4 步）：
       状态 = prev，行棋方 = prev.redToMove
       每步枚举 XiangqiRules.canMove 的合法走法，
       且移动子/落点必须落在 prev↔cur 差异格或平台变化格内；
       吃子、同型上限、最终盘面必须等于 cur；
       行棋方交替。
  3. 唯一解 → 逐手 record（颜色按实际移动子）；
     多解 → 优先用中间平台消歧；无平台时才用 markers 佐证；
     仍歧义 → 悬浮窗提示“疑似快速两步 A→B”，预填纠错弹窗让用户确认。
```

- 现有 `tryTwoSteps` 保留为 2 步快路径；新增 `resolveSequence` 处理 3-4 步；
- 每次移动的 `moverIsRed` 由实际移动子决定，不盲信轮走方；
- 每条记录落盘；若无法解释，走 4.4 的 rebase/缺口。

**复杂度**：差异格 ≤8，每步合法候选 ≤~20，4 步 ~160k 状态；只枚举涉及差异格的走法，实际远小。
**常见长度**：我方一步 + AI 0.5-1s 回子 = N=2；人类 1-3s 回子通常已被 3s 帧环的平台覆盖；N=3/4 仅兜底。

### 4.4 循环层：识别与引擎解耦

**识别循环**（持续、不阻塞）：

```
loop:
  frame = frameRing.awaitNewPlate(timeout)
  board = recognize(frame)
  seq   = resolveSequence(last, board, frameRing.plates, markers)
  record(seq) 或 rebase(board, 缺口)
  GameLiveState.update(...)
  analysisDispatcher.offer(latestFen, latestBoard)
```

**分析调度器**（独立 job）：

- conflated 最新局面；同一时刻只允许一个引擎搜索；
- 搜索完成的候选**必须带 FEN**；若与当前最新 FEN 不一致，只记日志，不上悬浮窗/知识库；
- 悬浮窗标“分析中（局面已更新）”；
- 复盘启动时 `cancelAndJoin` 分析 job，复用现有 `SearchMutex`。

**效果**：循环周期从 2-6s 降到 ~0.5-1.5s；快速连走不再盲区；推荐可能滞后，但棋盘/棋谱始终正确。

### 4.5 棋谱一致性：record / rebase / gap

- 任何 `last` 前进必须二选一：
  - 合法走子序列 → `record`；
  - 解释不了 → `recorder.rebase(pos)`：更新当前局面 + 标记“棋谱缺口”；悬浮窗提示可纠错；
- `replayPosition` 遇到缺口时，从缺口处改用 override FEN，后续走子继续推演；
- 纠错基准优先“最近识别盘/实况页”，其次 recorder 当前，再上一手之前；
- 撤回一步同步锚点与当前局面。

### 4.6 引擎层：预热、渐进、自适应

1. **进程级预热**：`EngineHolder`（进程级单例）在 `MainActivity/Application` 启动即加载 NNUE + warm-up；service 复用，不再等 onCreate。
2. **状态**：`LOADING(elapsed)/READY/FAILED`；悬浮窗显示“引擎预热 Xs / 就绪”；开局在预热中排队并提示。
3. **渐进首搜**：`SearchController` 解析 `info` 行，MultiPV 首套完整候选到达即回调；悬浮窗先上一条，最终结果覆盖。
4. **自适应 movetime**：warm-up 测实际速度；模拟器 600ms 实际 3.7s → 自动降到目标 ≤1.5s；手机保持 600ms；复盘 3000ms 不变。
5. **候选去重/收尾 wait/退化重搜**：保留 7290933 的实现。

### 4.7 复盘进度

- `OverlayView.setReviewProgress(done,total,elapsed)`：
  - 按钮文字 `复盘 3/17`；
  - 正文 `复盘 3/17 · 已用 42s`；
  - 完成切「下一局」；
- 实况页同步一行进度；
- 短局 1/1 明确显示。

## 五、分阶段实施

### S1：采集/帧比对 v2 + 木色判定 + 复盘按钮（最高优先）

- `ScreenCapture`：监听式采集，直接在 plane 上算 90 格细胞状态（60fps）；
- 新增 `FrameRing` + 动画状态机（STABLE/MOVING/PLATEAU/SETTLE）；
- 新增 `MoveMarkerDetector`（白圈/红圈，先只读输出，语义确认后参与决策）；
- `BoardWatcher`：origin-static 用木色首帧判定、cap 暖格不删；
- `OverlayView`：复盘按钮进度 `复盘 X/Y`；
- 标定：真实动画窗口落盘，确定 `PLATEAU_MS`/`SETTLE_MS`；
- 验收：动画结束后 ≤200ms 落定；中间平台 ≥80ms 可捕获；合法单步首帧通过；
  暖格永不被 cap 删除。

### S2：走子序列还原 + 识别/引擎解耦（2026-10-23 完成）

- `resolveSequence`：平台优先，1-3 步合法 DFS 兜底；
- `AssistantService`：分析 job + conflated 最新局面；循环不再 await 引擎；
- 验收：快速两手/三手 1.5s 内记账；推荐允许滞后但棋盘/棋谱正确。
- **已实现**：`SequenceSolver`（1-4 步合法 DFS，8k 节点预算）接入
  「重启对齐」与「implausible」两条路径；`dispatchAnalysis` 独立 job +
  `latestAnalysisFen` conflated 最新局面，识别循环不再 await 引擎。

### S3：4 步扩展 + 歧义交互 + 数据飞轮

- 4 步 DFS 上限、候选去重、歧义提示；
- 纠错弹窗预填“疑似序列”；
- cap/origin 拒绝帧、MOVING 窗口自动落盘，端局颜色/类型硬负样本入库，下一轮重训。

### S4：进程级引擎预热 + 渐进首搜 + 自适应

- **首推库优先（2026-10-23 已完成）**：KB 命中不再等引擎，秒出库着法，
  引擎就绪后 `scheduleBookFill` 后台补齐；实测开局首推 18s → 约 1s
- **快搜异常（2026-10-23 已定位并修复）**：实机 `fast search cost=29-90ms
  depth=3-7` 的根因是 JNI `nativeGo` 绕过 UCI 层、没设 `limits.startTime`，
  时间检查 `now-0` 立即 stop；补上 startTime 后按 movetime 真跑。
  同时修复帧环外的兜底抓帧导致的正反幽灵步（只认落定帧）。
- `EngineHolder` 进程级；状态显示；开局排队；
- `SearchController` 渐进回调 + 自适应 movetime；
- 验收：引擎在开局前就绪；首条候选 ≤1.5s；完整 ≤3.7s（模拟器）。

## 六、风险与回滚

| 风险 | 处理 |
|---|---|
| 解耦后推荐滞后/串局面 | 候选带 FEN，只有与最新一致才上屏；日志记录丢弃 |
| 4 步 DFS 误判 | 棋规+同型上限+唯一解；多解提示用户；可撤回 |
| 帧环内存/CPU | 只存指纹/木色/缩略；10-15fps 节流；上限 2-3s |
| 白圈/红圈皮肤差异 | 先确认语义；检测不到时退回平台/DFS |
| 进程级引擎常驻 | 明确生命周期（进程死亡释放）；可配置 |
| 大改回归 | 分阶段提交；每阶段单测+实机验证；保留旧路径开关 |
