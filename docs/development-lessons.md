# 开发经验沉淀

> 从开发对话与排查中沉淀的 durable 经验,按域分组,每条都是踩过坑的
> 结论而非通识。持续更新于每次排查后;个人向的鲜活上下文另见
> `~/.claude/projects/e--learn-auto-cheese/memory/`。
> **同一类病复发两次以上时,先查 [recurring-issues.md](recurring-issues.md)**。

## 一、方法论:先定位再修,修在正确的层面

1. **动画永远赢过识别层阈值**。JJ 的光圈脉动/落子标记使被罩棋子
   每分钟在两版识别间交替上百次,继续调 NCC 阈值追不上;最终解法在
   **循环层**做遮蔽容忍(仅消失=忽略,仅出现=修复锚点)。教训:识别
   "抖动"类问题先怀疑动画污染帧,在状态机层容忍,不要死抠像素。
2. **症状相同 ≠ 病因相同**。「等稳定棋盘画面」出现三种病因:白光圈
   空位误判、悬浮窗自身遮挡 row0、引擎无结果。逐帧落盘对比才区分开。
   排障利器:BoardWatcher 识别失败帧落盘 `files/dump/` → adb pull →
   PC 端用 `tools/proto_recognize.py` + `assets/cnn.onnx` 对**同一帧**
   复刻(CNN 时代;`diag_fresh.py` 是 NCC 时代工具,仅作历史参考)。
3. **验证口径必须与 App 实际管线一致**。PC 原型用 refine_grid 吸附
   网格、App 用 raw 双线性网格,导致 PC 全对、App 复现失败一轮。
   复现 bug 先取设备端真实数据再逐步模拟。
4. **"修了没生效"先怀疑 APK 陈旧**:assembleAndroidTest 不重编主包;
   gradle 后台任务可能卡在 install 前一步。判断办法:设备端行为
   与修复前完全一致 → 先查安装时间戳(`dumpsys package | grep lastUpdateTime`)。
5. **按钮坐标必然漂移**。改布局后所有自动化点击坐标失效;"按钮点了
   没反应"多半是坐标过时,先 `uiautomator dump` 重测,再怀疑代码。

## 二、识别/循环域

6. **三种遮挡源**(白光圈/悬浮窗/引擎时序)症状完全相同,分界:
   空位 std 抬高 → 光圈;矩阵 row0 持续 unknown → 悬浮窗位置;
   有候选但卡住 → 引擎。悬浮窗默认位 (270,1560) 就是为避开识别区
   (y≈455~1530) 调出来的,别乱动。
7. **幽灵步污染链**:空位光圈误判成假子 → 宽松步判定放行 → 记账消耗
   对方回合 → 后续真实走子被记到错误名下,FEN 永久毒化。三层防御:
   归因按移动子实际颜色、重置后确认期、异常显式提示。
8. **单格持续误读**(其余全对)优先怀疑校准文件而非算法:曾因
   calib_default.json 四角倾斜 11px,帅被逐帧读成炮,所有修复层
   (锚点/王格修复)都救不了"从启动起就没一帧可信"的局面。
   PC 端用两套四角跑 refine_grid 对比可一锤定音。
9. **不可能兵位**:JJ 点击棋子抬起悬空时被识别成兵出现在不可能行,
   用锚点修复;王被将军特效罩住同理(restoreMissingKings)。修复要设
   边界:王格出现**敌子**说明真被吃,拒绝修复。

## 三、引擎域

10. **引擎全局状态只有一个**:autoLoop 的搜索取消不了(native 轮询无
    挂起点),复盘前必须 `cancelAndJoin` 且整条 search 用 Mutex 串行,
    否则残留搜索与复盘交错 → 引擎状态污染 → 对局中途整体卡死。
11. **Pikafish 缺王 = SIGABRT 杀进程**:缺王 FEN 拦截 +
    `set_position` 返回值检查,两层都不能省。
12. **搜到 bestmove 才算结束**:movetime 到点即退会拿空 bestmove;
    stop 后引擎必然补发,再等 2s;go 前清空 nativePollLine 残留队列。
13. **JNI 集成三坑**(详见 memory/setup-lessons):setoption 输入流从
    "name" 开始;五个回调必须全注册(缺则 bad_function_call abort);
    JNI 下 std::cout 全丢,诊断必须接 __android_log_print。

## 四、UI/系统域

14. **瞬态文本会被 autoLoop 每帧覆盖**:「尚无对局记录」类提示只活
    不到 1 秒,自动化测试要在点击后立即截图,否则误判"点击无效"。
15. **可变对象做模板是雷**:`Position.START` 曾是带可变数组的单例,
    手摆棋子直接污染模板。共享数据结构暴露成 val 单例前问一句:
    内部数组是否可变?会被外部改吗?→ 改返回全新副本的取值器。
16. **Shape XML 的 radial 渐变必须写 gradientRadius**,否则旧设备
    inflate 直接崩(主界面打不开那次)。崩溃后第一时间抓
    `logcat -b crash` 的 InflateException 链。
17. **负 margin 上浮、悬浮窗窗口尺寸随内容变化**这类视觉技巧在
    LinearLayout 里不一定按预期渲染;上线前必须截屏核对
    (前一版书挡式的空藏蓝带就是渲染没跟上预期)。
18. **AppLog 模式**:三方包无 READ_LOGS,logcat 读不到自己的日志;
    排障必须落盘文件(会话命名+轮转+崩溃同步写钩子)。新增日志
    一律 AppLog.*,不要 android.util.Log(不落盘=事后无法回溯)。
19. **状态时序预检**:写多协程状态机(结/下一局/复盘/识别循环)前
    先想清楚"协程 A 在 B 未 join 时重入会怎样"。复盘复用引擎、
    下一局重识别,都是同一类竞态。

## 五、流程域

20. **每轮实机验证的固定动作**:build → install → 单按钮授权(授权成功
    自动启动;首次还需授予〈使用情况访问〉) → 切对局 → 核对悬浮窗;
    省一次来回的窍门是库内一把 grep 检查提交物是否含预期字符串
    (防陈旧 APK)。
21. **大重构前先出视觉稿给用户选**(HTML mockup + 截图),方向错了
    XML 写得再好也是返工;编辑部/棋馆/Bento/沉浸四稿定一稿,一次成型。
22. **写文档/提交物用拼写检查兜底**:曾混入葡语词"estrutura"到
    中文文档;IDE 未知单词提示值得扫一眼。

## 六、CNN 识别域(方案 A,2026-10)

23. **训练与推理必须逐参数同源**:同一张帧 PC 端 86/90 正确、App 端全盘
    低置信,根因是 App 用面积均值做 104→128 上采样(块复制马赛克),训练用
    PIL `BILINEAR`。Kotlin 端于是改写 4 邻点双线性。检查清单:插值方式、
    crop 边界取整、通道顺序、`(x/255-mean)/std`、是否 TTA、输入尺寸。
    对拍时优先拿 **App 自己落盘的帧**,不要用 adb screencap 代替。
24. **TTA 不是免费的**:水平翻转后棋子汉字成镜像,落在训练分布外;把翻转
    视图 logits 与原图平均,等于给次优类注入伪证据。实测每帧凭空多出第三个
    红车且 margin=1.0,把真子挤出上限。CNN 主路只做单次前向。
25. **懒推理缓存要逐格同步**:只重推理 dirty 格,却整体覆盖指纹数组,会让
    冻结期的分类与指纹永久错配。指纹数组与分类数组必须一一对应地更新。
26. **margin 定义跨端统一**:`margin = sigmoid(top1 - top2)`。训练导出、
    PC 入库脚本、Kotlin 推理三处必须同符号;曾因一处写成 `top2 - top1`
    导致 100% 拒判。
27. **模型验收用实时帧整批留出,不信随机 cell 划分**:同一帧的相邻格子近
    重复,cell 级随机 val 会泄漏。以 `Lmp_*` 实时帧整批留出为门槛:
    conf≥70% 覆盖全部可判格、硬错误=0 才收录。当前 Small@128 留出
    110/110、硬错 0、拒判 0。
28. **标签错一格,重训白一整轮**:行号 1 基/0 基混用曾把 9 个格子标进
    错误类别(红炮标成黑卒),模型照单全收。入库前先用坐标回问用户确认;
    发现错标要把样本搬到正确类别后重训,不能只改脚本。
29. **偶发错一格的兜底在仲裁层,不在模型**:分层置信(CONFIDENT≥0.9 /
    WEAK 0.75-0.9 / UNKNOWN)、变化格必须能解释成 1-2 步合法走法、
    同型棋子上限 + margin-prune、落定确认期——这些比继续调模型
    更能压住"每几十帧错一格"的尾巴。
30. **安装事件清盘**:FEN/棋谱/锚点跨进程持久化,重装后必须自动清,
    靠 `PackageInfo.lastUpdateTime` + 版本号比对,别指望用户记得
    「结 & 下一局」。

31. **红圈会把黑子读成红子**：JJ 的红色落点/威胁标记套在黑子上时，模型
    把黑车读成红车（同帧合成复现 0.94-0.99）。颜色是强物理先验：格内最暗
    18% 笔画的 `R-G` 黑子≈1-3、红子≈76-113，据此纠色；训练增强必须把
    红圈/绿圈同时套在黑子与红子上，否则模型学到的是"红圈=红子"。
32. **同型超限不能按 margin 删子**：`piece cap` 剔掉"多余的红车"时，被剔的
    可能是被颜色翻转的真黑车。正确顺序是先用期望局面（棋谱回放/recorder/
    START）逐格核对，核对不了就整帧作废 + 强制重推；删真子是最坏的失败。
33. **自动逃生门不能采纳"棋子凭空消失"的帧**：vanish-only×10 重锚、
    implausible×3 清谱、30s 强制接受残缺盘，三条都会把误读永久固化。
    改为保留锚点/棋谱 + 强制重推 + 悬浮窗提示，由用户「纠错/重试」放行。
34. **数据集要先去重再谈增强**：2542 张里 1408 张类内近重复（相邻帧同格），
    EMPTY 占 62%；去重后空位硬负样本每轮必进，重训后空位误报 46/67→0/67。
    验收口径用单次前向（与 App 一致），不要用 TTA 抬高数字。
35. **纠错入口要落在棋谱与锚点上**：浮窗四下拉输入一手棋后，必须同时写回
    recorder 与识别锚点，并重出推荐；只改实况页显示会被下一帧识别覆盖。

36. **残影幻步判定要用"上次接受局面帧"的快照**：旧实现拿 `Observed.snapAnchor`
    （上一帧快照）判 origin 是否静止；上一帧往往已经是走子后的画面，真走子
    会被永远判成 `origin static` 并拒绝（2026-10-22 实测黑卒 (3,6)→(4,6)
    连续 40 秒不出推荐）。改为在 AutoLoop 里随 `last` 一起保存 `lastSnap`，
    且快照是 raw 方向——执黑时 origin 格号要上下翻。

37. **引擎首搜必须等 NNUE 就绪**：`EvalFile` 的加载/校验是异步的，
    `setoption` 返回时网络可能还没 ready。JNI `nativeInit` 若直接返回，
    调用方立刻 `go()` 会在无网络状态搜索——返回深度1、单候选、评分0，
    首推固定「兵九进一 +0.0」（实测搜索 14:37:09.883，NNUE ready
    14:37:09.927）。修复：`set_on_verify_network` 置原子标志，
    `nativeInit` 等就绪（10s 超时）；Kotlin 侧对深度≤1/单候选/评分0
    且非杀的结果延迟 300ms 重搜一次。

38. **同一 root move 出现两条推荐 = stop 收尾残留**：`searchMutex` 只串行化
    Kotlin 调用，native 搜索线程在 `stop()` 后仍在收尾；下一轮 `go` 若此时
    发出，残留 info 行会串进本轮，`byRank` 里同一个着法占两个 multipv、
    评分不同（实测 `f0e1 仕四进五 +0.1` 与 `+0.3` 并列，搜索仅 52ms）。
    修复：JNI 暴露 `wait_for_search_finished`，每次搜索前后各等一次；
    结果按 root move 去重（深度高者优先，同深度保留排名靠前者）；
    另加 `fast search cost<movetime/2` 日志留证。

39. **期望局面回填必须有像素证据**：棋谱回放一旦漏记一次吃子，中局
    "期望有子、本帧空"的修复会每帧把已被吃的子补回来（实测实况页第三列
    多出两个车，日志连续 `expected-piece restore: (4,2)车, (5,2)车`）。
    正解是用**木色占比**裁决：棋子是暖色木盘（`R-B>40` 占比实测 0.56-1.00），
    空位是冷色石纹（0.00-0.02）。只有该格仍"有木色"才补；冷格说明真被吃/
    走开。vanish-only ×10 的重锚也用同一证据区分"误读"与"真消失"。
40. **引擎冷启动要预热，且不能阻塞识别循环**：NNUE 64MiB 在模拟器加载
    约 10s。旧版在 autoLoop 起始同步 `ensureController()`，点开局后 12s
    才消费标志、首推更晚。改为 service onCreate 后台预热 + 循环不等待 +
    启动后先跑 60ms 开局 warm-up（否则 NNUE 刚 ready 的首搜仍可能返回
    depth1/评分0）。预热期悬浮窗显示「引擎启动中」，开局按钮/Toast 立即响应。

41. **终局棋子数门不能写死**：`MIN_PIECES=10` 把「黑马吃红炮」后的 9 子
    残局当非棋盘画面，每帧 credibility fail——这步吃子因此永远记不上；
    用户纠错后同一道门继续拒绝 9 子盘，实况页对、悬浮窗却一直「等待」。
    正解：绝对下限降到 2（双王才是真不变量），再加相对门
    「本帧子数 ≥ 期望局面子数 - 2」（期望=棋谱回放/上次可信帧）；
    期望是 START 兜底且画面离 START 超过 6 格时不做相对比较。

42. **长任务必须给进度，不能只显示「进行中」**：复盘按每个用户行棋局面
    3000ms 深搜，模拟器上实际每次约 6s，34 步的一局要几分钟；悬浮窗只写
    「复盘中」会被当成卡死（2026-10-22 用户反馈）。`GameReviewer.review`
    增加 `onProgress(done,total)`，悬浮窗实时显示
    「复盘中 X/Y 个局面…」，完成后才切「下一局」。

43. **重试/循环重启必须先和棋谱对齐**：循环重启（重试/纠错/服务恢复）时
    新识别盘可能已经比棋谱多走了 1-2 步；旧版 `recorder.start(pos)` 直接
    以新盘为新起点、棋谱却保留旧记录 → 回放断裂、期望局面失真
    （2026-10-22 实测重试吞掉「进黑车 + 平红车」，之后 32 子期望卡死 29 子真盘）。
    修复：首帧先尝试把差异解释成 1 步/2 步合法走子并补记；解释不了就
    `recorder.setCurrentPosition` 以识别盘为当前局面并留“棋谱缺口”，
    悬浮窗提示可纠错——绝不静默跳过。
44. **静止画面不推新帧不是识别失败**：ImageReader 在静止画面上不推帧，
    `captureFresh` 超时 null 是正常现象。旧版 `waitForPosition` 直接
    return null → 对手思考/画面静止时悬浮窗一直「等待稳定棋盘画面」
    （实测 9s），用户以为卡死点了重试，才引出第 43 条的跳步。
    修复：没有新帧就复用上一帧继续识别；局面没变时循环保持现有推荐。
45. **期望局面必须有可信门**：棋谱回放可能因漏步失真（32 子），不能拿它
    做子数门/补子/超限核对的唯一依据。期望与本帧高置信格冲突 >8 即视为
    过期、忽略；期望来源优先 `recorder.lastFen()`（含纠错）、回放只作后备；
    纠错基准优先实况页/最近识别盘，而不是滞后 recorder。

46. **木色证据 > 过期期望 > 过期像素快照**（2026-10-23，S1a）：
    两处事故同一根因——拿旧证据删/卡当前真实的棋子。
    ① `piece cap` 超限核对用期望「空」+ 像素静止（相对旧锚点）删真子，
    实测 17:51 把 `(7,6)` 真黑马删成空；② origin-static 幻步防护只看
    像素快照，快照过期时真走子被当幻步，红马 `(9,7)→(7,6)` 空等 10 帧 9s。
    修复：超限核对增加暖格否决（`MoveCheck.canDropOverCap`：期望空但
    `R-B>40` 占比≥0.25 → 保留不删，整帧拒收重推）；origin 判定改为
    本帧木色裁决（`MoveCheck.rejectStaticOrigin`：出发格已冷 → 快照过期，
    首帧放行；仍暖 → 幻步拒收；无木色证据才沿用多帧保护）。
    通用口径：**实时像素证据（木色）优先于任何历史快照/期望**。

47. **复盘进度要落在按钮上**：正文「复盘中 X/Y」在短局（1/1）几乎看不到，
    用户仍以为卡死。`OverlayView.setReviewProgress(done,total)` 让「结」
    按钮直接显示「复盘X/Y」，正文补「已用 Ns」。

48. **落定判定看格心指纹，不看整帧像素；装饰单格不进入动画**（2026-10-23，S1b）：
    `ScreenCapture` 增加监听式细胞状态流（`CellSampler` 直接在 Image 平面采样
    90 格，20fps，不转 Bitmap、不跑 CNN），`MotionTracker` 按格心 4×4 指纹
    判断动画：非装饰格安静 160ms 落定、安静 80ms 记平台。
    关键取舍：
    - 格心采样 ±0.3 格，避开 0.45 格半径的白圈/红圈——光圈脉动是装饰，
      若采进指纹会让落定无限推迟；
    - 恰一格变化且前后都还是木色棋子 = 点选抬起/光圈套子 → 不算走子
      （否则按住棋子 1s 会落定出"抬起的假盘"）；
    - 悬浮窗矩形内的格恒零，窗文字动画不能触发落定；
    - 落定帧 Bitmap 才转（一次落定一次），队列上限 3 帧，防快棋堆积内存。
    识别循环先取落定帧直接识别，采集不可用/持续动画时自动回退旧的
    350ms×2 双帧等待——新旧两路共存，不设开关也能安全降级。

49. **静止画面不推帧 → 落定计时必须有心跳**：S1b 第一版只靠 `onFrame`
    累积"安静 160ms"，但动画结束后屏幕静止、ImageReader 不再推帧，
    安静计时永远到不了阈值——最常用的场景（AI 落子后我方思考 2-3s）
    反而不会落定。修复：`MotionTracker.tick(now)` 由 `pollSettle` 每 40ms
    推进安静计时；采集侧在安静 90ms 时**预转**一张落定帧，tick 落定时
    直接用它（`pendingSettle`），没有预转帧则回退抓帧。重试/暂停恢复时
    清空落定队列，避免消费过期窗口。
    另：`stopCellStream(owner)` 必须校验归属——重试用 `cancel()` 而非
    `cancelAndJoin()`，旧协程 finally 晚于新 watcher 启动，无校验会把
    新采集流关掉且新 watcher 不再重试。

50. **首推不要等引擎，知识库命中就秒出**（2026-10-23）：实测点「开局」到
    首推 18.3s = NNUE 加载 14s + warm-up 3.1s + 首搜 3.7s（模拟器）；
    而 `kb hit depth=12` 在 warm-up 结束时已经可用，旧逻辑却仍同步跑完
    3.7s 搜索才上屏。改为：KB 查询放在 `ensureController()` 之前，命中
    立即返回库着法；`scheduleBookFill` 在后台等引擎就绪再补两条，写回前
    用 `samePosition(fen)` 核对局面未变（否则丢弃）。无库命中才等引擎。
    库命中时首推从 18s 降到 ~1s；引擎补齐不阻塞识别循环。

51. **悬浮窗按钮是四态闭环，不是"结/下一局"复用**（2026-10-23 用户确认）：
    `局前(只有开局) → 局中(结+纠+实) → 复盘中(复盘X/Y) → 局前(只有开局)`。
    旧版局前同时显示「开局+结」、复盘完成显示「下一局」，语义混乱。
    实现：`setGameStarted(false)` 同时隐藏「结」；`showReviewingMode`/
    `setReviewProgress` 隐藏「纠/实/开局」；复盘完成与**失败/无棋谱**都
    回到局前态（失败分支必须留 `SealReview: ... back to idle` 日志）。

52. **局前零识别：识别循环由「开局」启动，不是服务启动就开**（2026-10-23
    用户要求）：旧版授权后立即 `startAutoLoop`，用户还没点开局就在跑 CNN、
    引擎分析，并弹「等待稳定棋盘画面 / 识别不稳定」——局前这些全是噪音。
    现在 `START_AUTO` 只亮悬浮窗（正文「点「开局」开始记账」），点开局才
    启动循环；引擎仍在后台静默预热（`ensureController(announce=false)`，
    库补齐同样不抢正文）。两个例外：进程中途恢复且棋谱已有走子 → 自动续上；
    「重试识别」按钮 → 显式重启。识别到完整 START 局面（未封存就开新局）
    时清谱并 `break` 停循环，等用户点开局再记账，不再继续识别。

53. **绕过 UCI 直调引擎必须补 startTime**（2026-10-23）：`nativeGo` 只设
    `limits.movetime`，`limits.startTime` 默认 0 → 时间检查
    `now()-0` 立刻 stop，实测每手 29-90ms、depth 3-7，复盘 3000ms 实际
    30-50ms。补一行 `startTime = steady_clock now` 后搜索才按 movetime 跑。
    以后任何直调 `Engine::go` 的桥都要对齐 UCI 入口的初始化（startTime、
    局面合法性、选项）。
54. **帧环开着时禁止"兜底抓帧"参与记账**（2026-10-23）：没有落定窗口时
    用 `captureFresh`/`lastBmp` 识别，会把动画中/落后的画面当新盘，
    同一子正反记 3 次。正确做法：无落定就原样返回上次局面；只有首次
    启动或长时间无落定（静止 1.5s、动画异常 3.5s）才兜底，且兜底结果
    也必须过走子校验。见 [recurring-issues.md](recurring-issues.md) 第 13 条。
55. **实况页 singleTask + 永远我执子在下**（2026-10-23 用户要求）：重复点
    「实」曾把 LiveGameActivity 叠多层，返回要按多次；Manifest 设
    `launchMode="singleTask"` 复用同一实例。棋盘显示加 `flipped`
    （只翻行不翻列，与 JJ 执黑显示一致），`GameLiveState.userIsRed` 由
    服务在 `postAnalysis`/换边时写入，实况页据此翻转；触屏纠正按视觉行
    反算，写入仍是规范局面。

56. **边条指纹只当提示，不当硬门**（2026-10-23 最终形态）：这个启发式
    指纹（JJ 对局页上下边条灰度）会把**真实走子的落定窗口**判成非对局界面
    ——实测每手棋都误判一次，日志 `边条指纹不符 top=… bot=… ×1` 紧跟
    `settle frame seq=N`，旧版直接丢弃窗口（丢步），中途加过"重试 2 次"
    又变成每手白烧 1.1s 延迟。最终做法：**容忍前 2 帧（继续走识别，由
    双王/子数/期望门把关），连续 3 帧不符才暂停，60 帧才重学指纹**；
    识别成功即复位 `mismatchRun`。真正"不是棋盘"的画面由 credibility
    门拦住，不需要这层猜。

57. **识别循环不能 await 引擎**（2026-10-23，S2 前半）：`postAnalysis` 里
    同步 `analyzeCandidates` 让循环每步停 movetime（修复 startTime 后是
    真 600ms+），这期间不抓帧——对方秒回的两步就挤进同一窗口，也让落定
    窗口在队列里堆积。改为 `dispatchAnalysis`：识别循环立刻返回处理下一个
    落定窗口；分析在独立 job 里跑，结果回来时用 `latestAnalysisFen`
    核对局面是否已变，变了就丢弃（conflated 最新局面）。复盘/开局时
    `analysisJob` 一并取消，防旧局结果写回新局悬浮窗。

58. **别用"重试/延迟"掩盖一个错的门**（2026-10-23 教训）：边条指纹误判
    导致丢步后，先加了 `deferredSettle` 重试（无上限→活锁，同一窗口重试
    14 次、5 秒，用户被引去点「重试识别」，重启后 `rebase with gap` 连丢
    两步）；加上限后仍每手白烧 1.1s。真正的问题是**这个门本身判错了**，
    最终把它降级为提示（容忍 2 帧/连续 3 帧才暂停），并删掉整套重试机制。
    通用纪律：出现"偶发失败"时先怀疑判据，不要先加重试与补偿。

59. **多步缺口用合法序列还原，不猜**（2026-10-23，S2 后半）：循环重启/
    识别暂停后一次看到 3-4 手时，旧的 1-2 步分解解释不了就留"棋谱缺口"
    （`restart reconcile: unexplained diff ... rebase with gap`）——那几步
    永久丢失。新增 `SequenceSolver`：迭代加深 1-4 步 DFS，三条硬约束剪枝
    （每步最多改 2 格 → `diffCount > 2*剩余步数` 剪掉；起点必须是错位子
    或本支路刚移动到的格；落点必须是差异格或双方都空的过渡格），
    每步过 `XiangqiRules.canMove`，**终局盘面与轮走方必须完全一致**，
    否则返回 null 继续走缺口路径。节点预算 8k（约几十毫秒）防慢机卡顿。
    纪律：还原出的序列即使中间归因有偏差，终局一定正确——这比丢步安全。

60. **改判必须过物料不变量**（2026-10-23）：颜色门把红车判成黑车
    （R-G=31.5 落在 35 阈值内），仲裁层两帧确认后采纳 → 黑方凭空多一个车，
    棋谱永久错乱、`implausible` 空转不恢复。两道防线：
    ①`BoardRepair.fixColors` 用期望局面（棋谱）纠正**同兵种异色的静态格**
    ——颜色在象棋里永不改变；②`MoveCheck.exceedsMaterialCount` 拒绝任何
    让某方某兵种数量增加的改判（棋子只减不增）。另加逃生门：`implausible`
    连续 4 轮就以识别盘继续 + 留缺口提示纠错，不再无限空转。
    通用纪律：改判/纠错类逻辑都要有"物理不变量"兜底（数量、位置、颜色），
    只靠置信度与阈值一定会漏。

61. **多解要枚举并让用户确认，不能静默取第一条**（2026-10-26，S3）：
    3-4 步还原常有多条合法解释（同色两步互换先后、同名子互换角色），
    终局盘面相同但归因不同。`SequenceSolver.solveAll` 枚举（上限 8），
    用落定平台（中间稳定帧的变化格集合，`scoreByPlateaus`）先消歧；
    仍歧义就弹列表式确认框（`① 红 车四进一 → 黑 卒7进1`），用户点一条；
    20 秒未选按第 1 条，10 秒冷却防连弹。**不要用四下拉**——用户要的是
    直接选序列。确认即带真值标签，落盘 `files/labels/` 供重训。

62. **纠色不能覆盖走子差异**（2026-10-26）：`fixColors` 用旧棋谱纠正"静态格
    的同兵种异色"，但"静态"是灰度快照判的——同格红车↔黑车灰度几乎相同，
    用户刚吃子落下的红车被当成误配色改回黑车，整盘错乱。
    改成：只有整帧与棋谱的差异**全部**是同兵种异色才纠；出现变空/多子
    （走子/吃子的特征）一律放弃。通用纪律：按旧状态修新观测前，先确认
    新观测里没有走子差异。

63. **Android 14 的 MediaProjection 三条硬要求**（2026-10-26 真机闪退）：
    ① 必须先有 `foregroundServiceType="mediaProjection"` 的前台服务并
    `startForeground(..., FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION)`，
    再调 `getMediaProjection()`——否则点「立即开始」直接 SecurityException；
    ② `createVirtualDisplay()` 之前必须注册 `MediaProjection.Callback`，
    否则 IllegalStateException；③ 停止前台服务后投屏随即失效，`onDestroy`
    必须 `ScreenCapture.stop()`，否则 `isRunning` 是假状态，下次启动拿着
    失效的投影空转（表现为"校准了也不出推荐"）。
    另外主圆钮是开关，运行中再点会**停止**服务——必须给提示并把按钮文字
    切到「停止实战辅助」，否则用户以为坏了。
